结论先说：四个平台都“有可能做”，但不应做成四个独立的仿写爬虫。最稳的路线是：

> CreatorHub 负责浏览器、Profile、任务队列、限速、熔断和证据采集；平台专用 skill 负责采样协议、问题集、字段解释、指标和报告。

也就是推荐 `(c) 两层架构`，但生产执行统一收回 CreatorHub，Node/OpenCLI 版本作为探针、参考实现或临时兼容后端。

需要说明：按你的要求，本轮不做实时页面核验。因此下面涉及当前网页 UI、登录方式、引用按钮名称的部分，都是架构判断，不是对 2026 年 10 月线上界面的事实确认，均应通过真机探针验证。

## 1. 四个平台的可行性判断

判断不能只看“能不能输入问题”，而要分三层：

1. 能否稳定登录并保持会话；
2. 能否稳定提交问题并拿到完整回答；
3. 能否拿到可审计的引用、信源和追问链。

前两层四个平台大概率都能做，第三层差异最大。

| 平台 | 首选方式 | 总体判断 | 最大难点 |
|---|---|---|---|
| 千问 | Web 优先 | 可做，适合作为第一个平台 | 引用面板、联网模式和追问路径的实际 DOM 结构 |
| Kimi | Web 优先 | 可做，技术上中等偏稳 | 长回答、深度研究、虚拟化内容和流式完成判断 |
| 元宝 | Web 优先，App 备用 | 可做，但不确定性较高 | 微信生态信源是否真正暴露在网页 UI 中 |
| 文心 | Web 优先，App 备用 | 可做，但优先级最低 | 产品入口、页面版本、联网引用能力可能变化 |

### 千问

**登录与登录态**

大概率使用阿里系账号体系，可能包含扫码、手机号或其他统一身份登录方式。具体登录入口、是否依赖淘宝/支付宝/阿里账号体系，必须真机确认。

Cookie、Local Storage 或浏览器 Profile 理论上可以保持登录，但存在：

- 设备重新验证；
- 异常登录确认；
- 长时间未使用后失效；
- 浏览器 Profile 与设备环境绑定。

建议把“浏览器重启后仍可用”和“隔 24 小时、72 小时、7 天后仍可用”分开测试，不能只验证一次登录成功。

**提问 UI**

预计会有：

- 左侧历史会话；
- 新会话入口；
- 文本输入框；
- 发送按钮；
- 流式回答；
- 联网搜索、深度思考或类似模式选项；
- 追问输入区域。

这些是产品形态上的合理推测，具体按钮是否存在、是否在不同账号下出现，需真机探针验证。

**引用与信源**

千问比较适合作为第一批，原因是它的联网问答和阿里生态信源具有较强的 GEO 研究价值。

需要特别探测：

- 引用是否直接显示在答案中；
- 是否有可展开的来源卡片；
- 来源是否有标题、域名、摘要、链接；
- 是否可以点击查看来源；
- 搜索开关关闭时是否仍然展示来源；
- 追问后来源列表是否变化；
- 是否能区分普通网页、新闻、电商或阿里生态来源。

不能把“答案里出现了一个阿里域名”直接等同于“阿里生态信源占比”。必须记录 UI 明确显示的来源类型和分类置信度。

**反自动化风险**

预计存在常规的登录校验、设备校验、频率限制和验证码风险。不要通过切换 IP、伪造指纹、隐藏接口或验证码绕过来解决。

**判断**

千问适合 Web 采样，暂时没有理由直接上 App。只有在网页无法展开引用、联网模式无法操作或来源链接只在 App 中暴露时，才做 App 探针。

### Kimi

**登录与登录态**

大概率支持手机号、扫码或第三方账号登录，具体入口需探针确认。浏览器 Profile 持久化应该可行，但同样需要测试设备验证和长时间闲置后的失效情况。

**提问 UI**

Kimi 的主要特殊性不在普通问答，而在：

- 长文本回答；
- 深度搜索或研究型回答；
- 文档、网页或附件相关能力；
- 回答持续时间较长；
- 可能有虚拟化消息列表；
- 回答内容可能动态追加、分段渲染。

因此不能用“发送后等待固定几秒”判断结束。应该检测：

- 生成状态是否结束；
- 停止生成按钮是否消失；
- 回答内容是否在稳定窗口内不再变化；
- 长回答是否已经全部加载；
- 页面滚动或虚拟列表是否导致内容暂时不在 DOM 中。

**引用与信源**

Kimi 的引用可能出现在：

- 回答中的脚注或链接；
- 来源卡片；
- 研究结果侧栏；
- 可展开的来源区域；
- 文档或网页引用区域。

需要分别验证“引用可见”和“引用可结构化提取”。有些引用视觉上可见，但链接信息可能需要点击后才能获得；也可能只保留标题而没有 URL。

**反自动化风险**

主要风险不是单纯的验证码，而是：

- 长回答超时；
- 页面内容未完全加载；
- 连续问题导致会话状态异常；
- 研究模式耗时较长；
- 页面虚拟化造成重复或漏抓。

**判断**

Kimi 适合 Web 采样，不建议一开始使用 App。它的核心难点是长文采集和引用完整性，而不是必须依赖移动端。

### 腾讯元宝

**登录与登录态**

大概率存在腾讯账号、手机号或微信扫码等登录路径。微信扫码往往会增加设备确认、登录过期和人工确认环节，具体需要探针验证。

**提问 UI**

预计包含：

- 会话列表；
- 新会话；
- 输入框；
- 普通回答或深度模式；
- 联网搜索；
- 引用或来源区域；
- 追问。

但元宝的功能可能随产品版本、账号类型、地域和灰度发布变化，不能假设所有账号看到同样的模式按钮。

**引用与信源**

元宝最值得做的是微信生态和腾讯生态来源分析，但这里有一个关键区别：

> 元宝与微信生态关系密切，不代表网页回答一定会显式展示公众号、视频号或腾讯内容来源。

需要探测：

- 是否显示公众号来源；
- 是否显示视频号或视频内容来源；
- 是否显示腾讯新闻、腾讯文档或其他腾讯产品来源；
- 来源卡片是否给出账号名、发布时间、内容类型；
- 是否能点击到原始内容；
- 追问是否会从一般网页转向公众号、视频号或其他腾讯来源。

如果网页只返回一个普通回答，而没有明确来源，不应该凭域名或内容语气推断“微信生态占比”。

**反自动化风险**

元宝的风险可能集中在：

- 微信扫码和设备确认；
- 腾讯侧统一风控；
- 页面和 App 能力不一致；
- 引用卡片使用复杂动态组件；
- 账号登录状态与微信设备状态关联。

**判断**

元宝可以先做 Web 版，但应从一开始就设计 App 降级方案。它是四个平台中最需要验证“网页是否足以完成采样”的一个。

### 文心一言

**登录与登录态**

大概率使用百度账号、扫码、手机号等身份体系，但产品入口和页面名称可能发生变化。代码中不要把“文心一言”和某一个固定域名写死，探针要记录实际最终 URL、产品名称和页面版本。

**提问 UI**

一般会有：

- 新会话；
- 输入框；
- 流式回答；
- 联网搜索、深度搜索或类似模式；
- 引用链接或来源区；
- 追问。

但这些能力是否默认开放、是否随账号开放，以及来源是否可见，都需要验证。

**引用与信源**

文心适合关注百度生态：

- 百度百科；
- 百度知道；
- 百度文库；
- 百度新闻；
- 百度系搜索结果；
- 百度自身知识服务。

但必须以 UI 明确展示为准。尤其要区分：

- “回答使用了百度搜索”；
- “回答中引用了某个百度产品”；
- “来源本身来自百度生态”。

**反自动化风险**

可能包括登录设备验证、页面版本变更、账号权限差异、搜索模式灰度和验证码。

**判断**

文心可以做 Web 版，但应排在后面。App 只有在网页版无法稳定登录、无法触发搜索模式或引用不可见时再考虑。

## 2. “专门针对”不能只体现在选择器

真正的平台专用，至少要体现在四层：

1. 会话模式；
2. 问题集；
3. 采样字段；
4. 分析指标。

选择器只解决“怎么点”，不能解决“采什么、怎么解释”。

### 千问专用协议

重点是“联网答案、来源构成、追问后来源变化”。

建议记录：

- 联网开关状态；
- 深度搜索或研究模式；
- 来源数量；
- 来源标题、域名、类型；
- 阿里生态来源是否被 UI 明示；
- 来源在答案中的位置；
- 追问前后来源变化；
- 推荐理由是否基于来源；
- 电商、内容、新闻、百科类来源的分布。

问题集应覆盖：

- 品牌推荐；
- 品类比较；
- 购买决策；
- “有哪些值得选择”的列表型问题；
- 追问“为什么推荐它”；
- 追问“给出来源”；
- 带时间限制的最新问题。

### Kimi 专用协议

重点是“长文深度回答、研究过程和文档/网页引用”。

建议记录：

- 首字延迟；
- 完整回答耗时；
- 回答长度；
- 章节或段落数量；
- 是否发生截断；
- 引用是否绑定到段落；
- 引用来源数量和多样性；
- 深度研究或搜索模式；
- 追问后观点是否发生变化；
- 来源是否从普通网页转向文档、论文或专业站点。

问题集应覆盖：

- 多步骤研究问题；
- 需要综合多个来源的问题；
- 长文解释型问题；
- 事实核验问题；
- 要求比较不同方案的问题；
- 对同一结论连续追问证据的问题。

### 元宝专用协议

重点是“微信、腾讯和内容生态信源”。

建议记录：

- 来源是否被标注为公众号；
- 是否出现视频号、腾讯新闻或其他腾讯内容；
- 来源账号名；
- 内容类型；
- 发布时间；
- 来源链接是否可点击；
- 来源预览是否包含摘要；
- 追问后是否增加腾讯生态信源；
- 普通网页和腾讯生态来源的比例。

问题集应覆盖：

- 国内品牌口碑；
- 本地生活；
- 行业资讯；
- 微信公众号常见的知识型问题；
- 视频内容容易影响答案的问题；
- “最近有哪些讨论”“哪些账号在讲”等内容发现型问题。

注意：没有显式来源标签，就记录为“未观测到”，不能推断为“没有”。

### 文心专用协议

重点是“百度生态、搜索新鲜度和实体消歧”。

建议记录：

- 联网/搜索模式；
- 搜索结果或引用数量；
- 百度生态来源类型；
- 新闻、百科、知道、文库等来源分类；
- 来源新鲜度；
- 品牌名与实体是否混淆；
- 回答是否给出可验证链接；
- 追问后是否改变实体理解；
- 事实型问题与推荐型问题的差异。

问题集应覆盖：

- 品牌实体消歧；
- 最新新闻；
- 公司和产品事实；
- 百度生态内常见资料；
- 负面信息和争议问题；
- “给出依据”或“列出来源”的追问。

建议所有平台都有一组相同的基础问题，用来横向比较；再叠加平台专用问题包。否则平台差异和问题差异会混在一起。

## 3. 三种形态怎么选

### 独立 skill 包

优点：

- 可以快速复用姚氏 Node/OpenCLI 方案；
- 平台之间隔离；
- 探针阶段开发快。

问题：

- 会重复实现 Profile、登录态、限速和任务队列；
- 与 CreatorHub 的账号隔离容易不一致；
- 任务和报告数据分散；
- Node 与 Python 之间要维护两套契约；
- 出现风控时，执行层和运营层无法统一熔断。

适合做探针和早期验证，不适合作为长期生产主路径。

### CreatorHub 内部模块

优点：

- 复用 Patchright、系统 Chrome CDP；
- 复用 Profile 隔离；
- 复用任务队列、冷却、失败重试和日志；
- 可以和抖音、小红书等运营账号做权限隔离；
- 本地部署和数据保留方式一致。

问题：

- 会增加 CreatorHub 的复杂度；
- 采样任务与社媒运营任务需要严格隔离；
- GEO 采样可能是长时间任务，不能影响运营队列；
- 数据库和报告模块需要扩展。

适合作为执行层。

### 两层架构

这是推荐方案：

**CreatorHub 执行层**

负责：

- 浏览器和 Profile；
- 登录状态；
- CDP/Patchright；
- 任务调度；
- 低频限速；
- 风控冷却；
- 截图、DOM、可访问性和原始记录；
- 熔断和人工接管。

**平台专用 skill/方法层**

负责：

- 平台能力定义；
- 平台专用问题集；
- 追问路径；
- 引用分类；
- 指标解释；
- 报告模板；
- 与行业标准对应的采样计划。

Skill 不一定要继续承担完整的浏览器驱动。它更适合成为“方法协议包”和“报告规则包”。

### Node/OpenCLI 与 Python/Patchright 的处理

不建议现在把两套代码硬拼在一个进程里。代价主要有：

- 两套异步模型；
- CDP 会话争抢；
- 同一个 Chrome Profile 的锁冲突；
- Cookie、Storage 和浏览器上下文不可直接假设兼容；
- 任务队列和重试逻辑重复；
- JSON 版本漂移；
- 出错时难以判断是浏览器、Node 还是 Python 的问题。

推荐迁移路线：

1. 先把豆包、DeepSeek 的输出整理成统一契约 v2；
2. 姚氏 Node crawler 作为探针和参考实现；
3. 新平台先用统一契约验证采样结果；
4. 生产适配器逐个平台迁入 CreatorHub/Python；
5. Node 版本保留到 Python 版本完成结果对照；
6. 一个 Profile 在同一时间只能由一个浏览器执行后端拥有。

如果某个平台只能通过 OpenCLI Browser Bridge 稳定访问，可以把 Node 作为独立 worker，但由 CreatorHub 调度，不能让 Node 和 Patchright 同时控制同一个 Profile。

## 4. 共享核与平台适配器

推荐的数据流是：

> 问题集版本 → 调度器 → 平台适配器 → UI 证据采集 → 统一记录 → 平台分析 → 报告

### 共享核应该包含

**问题集管理**

- 问题集版本；
- 问题 ID；
- 意图类型；
- 品牌、品类和竞争对手；
- 问题变体；
- 是否需要追问；
- 目标模式；
- 期望观测的来源类型。

**采样调度**

- 时间窗口；
- 重复次数；
- 低频间隔；
- 单账号并发限制；
- 失败重试策略；
- 任务暂停和人工恢复；
- 平台级、Profile 级预算。

这里的随机间隔应该服务于样本独立性和低频运行，不应被设计成规避风控的手段。

**统一会话状态机**

至少要能区分：

- 未登录；
- 已登录；
- 新会话准备完成；
- 输入成功；
- 已发送；
- 正在生成；
- 生成完成；
- 引用待展开；
- 需要人工处理；
- 遇到验证码；
- 被限流；
- 页面结构异常。

**证据采集**

- 原始回答文本；
- DOM 或可访问性快照；
- 截图；
- 引用面板截图；
- 来源链接和标题；
- 追问关系；
- 时间戳；
- 解析器版本；
- 失败原因。

原始记录中不要保存 Cookie、Token 或完整浏览器敏感数据。

**统一分析**

- 品牌提及率；
- 精确提及、别名提及、竞品提及；
- 推荐出现率；
- 列表中的位置；
- Top1/3/5；
- 回答立场；
- 来源数量和类别；
- 来源域名覆盖；
- 追问后的变化；
- 时间窗口之间的变化；
- 解析置信度。

“排名”只在回答明确出现有序推荐或列表时计算。没有列表的回答不能把“未出现”当成排名靠后。

### 平台适配器负责

适配器应该不是一堆散落选择器，而是一个带能力声明的状态机。

建议接口概念包括：

- `open_session`
- `check_login_state`
- `new_chat`
- `configure_mode`
- `submit_question`
- `wait_until_complete`
- `capture_answer`
- `expand_citations`
- `capture_citations`
- `start_follow_up`
- `capture_follow_up`
- `detect_login_expiry`
- `detect_challenge`
- `detect_rate_limit`
- `capture_evidence`
- `close_session`

每个平台还要声明：

- 是否支持联网模式；
- 是否支持引用；
- 引用是否可点击；
- 是否支持追问；
- 是否支持附件；
- 是否支持深度研究；
- 是否支持 App 后端；
- 哪些能力只能人工确认。

### 统一 JSON 契约如何扩展

不要把四个平台的字段全部摊平，否则后续会不断改表。

建议在豆包现有契约上做兼容扩展：

| 区域 | 作用 |
|---|---|
| `contract_version` | 统一契约版本 |
| `platform` | qianwen、kimi、yuanbao、wenxin 等 |
| `adapter_version` | 平台适配器版本 |
| `session` | Profile 引用、登录状态、模式、会话 ID |
| `query` | 问题、问题 ID、变体、重复编号 |
| `answer` | 原文、段落、完成状态、耗时、长度 |
| `citations` | 引用状态和来源列表 |
| `follow_up_chain` | 追问及父子关系 |
| `observations` | 提及、推荐、位置、立场 |
| `evidence` | 截图、DOM、可访问性快照、原始文件引用 |
| `errors` | 登录、限流、验证码、解析失败 |
| `platform_specific` | 平台专有字段 |

`citations.status` 必须至少区分：

- `captured`：引用可见且已提取；
- `visible_unparsed`：视觉上可见，但结构化提取失败；
- `none_shown`：已确认界面没有展示引用；
- `not_visible`：当前模式或页面未能观察到；
- `not_attempted`：本次没有尝试展开；
- `unknown`：页面状态不足以判断。

这是非常重要的。否则“没有引用”和“工具没抓到引用”会被混为一谈。

来源对象建议包含：

- 标题；
- URL；
- 域名；
- 页面类型；
- UI 显示的来源标签；
- 在回答中的位置；
- 是否可点击；
- 捕获方法；
- 分类置信度。

`platform_specific` 中可以放：

- 千问的联网模式、阿里生态标签；
- Kimi 的研究模式、长文段落引用；
- 元宝的公众号、视频号、腾讯生态标签；
- 文心的百度生态来源类型。

这样既统一，又不会牺牲平台特征。

## 5. 正式开发前的真机探针

探针的目的不是压力测试，而是确认“这个平台是否值得做、能做到哪一层”。

### 所有平台都做的公共探针

**登录探针**

- 用户本人手动扫码或登录；
- 记录实际登录方式；
- 关闭并重新打开浏览器；
- 观察 24 小时、72 小时、7 天后的会话状态；
- 测试登录失效时页面表现；
- 不自动填写验证码、不自动处理安全确认。

**新会话探针**

- 打开新会话；
- 输入一条短问题；
- 提交；
- 记录流式开始、持续、结束；
- 保存完整回答；
- 再开一个新会话，确认历史会话不会串数据。

**引用探针**

- 同一问题测试无联网模式和联网模式；
- 观察引用是否出现；
- 展开引用；
- 点击一个来源；
- 返回原回答；
- 记录标题、URL、来源类型和可见性。

**追问探针**

至少做一条三到五轮的链：

1. 基础问题；
2. “为什么这样推荐”；
3. “给出来源”；
4. “有没有不同观点”；
5. “请比较两个候选项”。

记录每一轮答案、引用、推荐顺序和来源变化。

**低频连续探针**

可以做一组 10 问，但不是并发刷 10 问。初次探针建议：

- 一个 Profile；
- 一个活动会话；
- 保守间隔；
- 不超过预设问题数；
- 遇到验证码、429、403、设备确认立即停止。

**重启探针**

浏览器重启后重新挂载 Profile，确认：

- 会话是否还在；
- 历史会话是否还在；
- 当前会话是否能继续；
- 任务恢复后是否会重复提交。

**双采集方式**

至少用两种方式交叉检查：

1. DOM/可访问性结构化采集；
2. 截图或视频的视觉复核。

对于引用，截图能证明“页面看到了引用”，但不能替代 URL 提取。因此报告中要区分“视觉确认”和“结构化确认”。

### 千问专项探针

- 联网开关；
- 搜索结果或来源面板；
- 阿里生态来源是否有明确标签；
- 追问后来源变化；
- 一条推荐型问题和一条事实型问题；
- 来源是否能点击并返回。

### Kimi 专项探针

- 普通短回答；
- 长篇研究回答；
- 回答中途滚动；
- 生成结束判断；
- 页面重新打开后内容是否完整；
- 引用是否绑定到段落；
- 研究模式是否比普通模式有不同来源。

### 元宝专项探针

- 微信扫码登录；
- 网页端和 App 端是否能力一致；
- 公众号来源；
- 视频号来源；
- 腾讯新闻或其他腾讯生态来源；
- 来源卡片能否打开；
- 追问后是否发生来源生态迁移。

### 文心专项探针

- 实际最终入口 URL；
- 搜索/联网模式；
- 百度百科、知道、新闻等来源；
- 来源是否有链接；
- 新旧产品名或页面版本；
- 实体消歧问题；
- 搜索结果的新鲜度。

### 探针验收门槛

建议设置三个级别：

**可作为自动化适配器**

- 10 次低频提问中至少 8～9 次完整完成；
- 关键状态可识别；
- 生成结束可判断；
- 登录失效和验证码可以被识别并停止；
- 原始答案和证据可保存。

**可作为引用分析适配器**

- 引用在界面上稳定出现；
- 可结构化提取标题、链接或来源标签；
- 至少 90% 的可见引用可以保存；
- DOM 与截图复核结果基本一致。

**只能作为半自动适配器**

- 用户需要手动处理登录、验证码或引用展开；
- 工具负责输入、等待、记录和导出；
- 引用无法完整提取时，报告明确标记为“答案采样”而不是“引用完整采样”。

## 6. 与 CreatorHub 的集成顺序

我建议的默认顺序是：

> 先统一契约和探针 → 千问 → Kimi → 元宝 → 文心

### 阶段 0：先处理共享层

不要一开始就改四个平台。

先做：

- 将豆包、DeepSeek 的现有输出映射到契约 v2；
- 保留原有报告兼容；
- 建立统一的 Profile、任务、证据和错误模型；
- 加入验证码、限流和页面异常熔断；
- 用已有豆包、DeepSeek 作为回归样本。

### 阶段 1：千问

千问适合第一个新适配器，理由是：

- GEO 价值明确；
- 联网和引用分析价值较高；
- 能建立第一套“来源可见性”标准；
- 能验证共享契约是否足够。

验收：

- 手动登录、Profile 隔离；
- 新会话、回答、追问完整；
- 联网模式可控；
- 引用状态可区分；
- 三个时间窗口重复采样；
- 单个核心指标至少 30 次有效观测；
- DOM/可访问性与截图至少两种方式交叉验证。

### 阶段 2：Kimi

Kimi 的价值在长文、研究型回答和文档引用，适合作为第二个适配器验证复杂回答处理能力。

验收：

- 长回答不截断；
- 生成完成可识别；
- 回答段落可保留；
- 研究模式和普通模式可区分；
- 引用与段落关联；
- 追问链可回放；
- 同样完成三时间窗口和 30 次有效观测要求。

### 阶段 3：元宝

元宝和 CreatorHub 的国内社媒运营场景联系最强，但技术不确定性也更高。

验收重点：

- 微信扫码和会话恢复；
- 公众号、视频号、腾讯生态来源是否真的可见；
- 来源类别不靠猜测；
- Web 不足时可人工接管；
- App 是否需要作为补充采集后端；
- 至少有一套“答案采样”和一套“引用采样”的清晰边界。

如果元宝探针发现其网页引用能力明显强于 Kimi，可以在探针阶段后把它提前到第二阶段，但默认不建议在未知网页能力前直接投入最多开发资源。

### 阶段 4：文心

文心放最后，主要原因不是没有价值，而是入口、产品版本和引用能力更可能变化。

验收重点：

- 实际产品入口稳定；
- 百度生态来源可分类；
- 搜索模式可重复触发；
- 引用不可见时不会伪造完整信源报告；
- 适配器与其他平台隔离，页面改版不影响共享核。

如果探针确认文心只能可靠拿到答案，拿不到来源，可以先发布“答案提及率版”，不把完整引用分析作为阻塞条件。

## 7. 风险与红线

### 账号必须分离

采样账号和运营账号建议严格分离：

- 独立浏览器 Profile；
- 最好独立手机号或身份体系；
- 独立任务队列；
- 独立限速预算；
- 独立日志和证据目录。

原因有三个：

1. 采样行为可能影响运营账号的安全评分；
2. 运营内容会污染采样结果；
3. 触发风控时可以隔离损失。

不要在采样账号中同时做大量运营、评论、私信或批量发布。

### 不做风控绕过

红线应明确写进产品设计：

- 不绕过验证码；
- 不破解登录；
- 不调用隐藏 API；
- 不伪造浏览器指纹；
- 不做代理轮换来规避限制；
- 不做账号农场；
- 不在出现挑战后自动重试；
- 不通过生成互动内容去影响被测平台答案。

遇到验证码、设备确认、明显限流时，任务立即暂停，等待人工处理。

### 频率策略

平台没有统一的“安全上限”，因此不要硬编码一个全平台通用数字。

初期建议：

- 单 Profile 单平台单并发；
- 低频间隔，优先从 5～20 分钟级别开始；
- 每次运行限制问题数；
- 30 次有效观测分布在至少三个时间窗口；
- 不把所有重复样本集中在几分钟内；
- Kimi 等长回答平台应以任务完成为准，不能按短问答平台的超时标准处理。

频率逐步调整必须以平台条款、实际挑战率和失败率为依据，而不是为了提高吞吐量。

### 熔断设计

出现以下任一情况，立即停止当前 Profile：

- 验证码；
- 403、429 或设备确认；
- 登录状态异常；
- 页面出现安全校验；
- 连续空回答；
- 页面结构大面积变化；
- 同一问题重复提交风险；
- 解析器无法判断是否已经完成。

应该有：

- Profile 级熔断；
- 平台级熔断；
- 全局紧急停止；
- 人工确认后恢复；
- 原始证据保留；
- 不自动删除失败记录。

### 数据安全

回答、截图和问题集可能包含客户品牌、内部资料或账号信息，因此：

- 默认本地保存；
- 不记录 Cookie 和 Token；
- 截图中尽量隐藏个人身份信息；
- 报告导出时做脱敏；
- 设定原始证据保留周期；
- 区分“原始证据”和“对外报告”。

## 最终推荐

我建议正式拍板为：

1. **四个平台都先做 Web 探针，不先做 App 主路径。**
2. **CreatorHub 作为唯一生产执行层。**
3. **四个平台各自拥有专用适配器、问题集和分析规则。**
4. **skill 包保留为方法与报告层，不再复制一套长期浏览器执行框架。**
5. **优先顺序：千问 → Kimi → 元宝 → 文心。**
6. **豆包和 DeepSeek 先作为契约和报告回归基线。**
7. **引用不可见时必须诚实降级为“答案采样”，不能把未抓到的引用当成没有引用。**

这样做的核心收益是：页面选择器可以变化，但采样方法、证据链、报告口径和风控边界不会随着每个平台重复散落。
